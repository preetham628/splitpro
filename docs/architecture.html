Architecture

How a chat message becomes a settled bill: auth, membership and roles, the agent's tool-calling loop, the expense-approval workflow, persistence, and the settlement math.

Source layout

main.pyStandalone CLI — runs ChatAgent in a terminal loop, no server, auth, or multi-user behavior involved.

Authentication

SplitPro uses Google OAuth (authorization-code flow) for sign-in, and its own signed JWT in an httpOnly cookie for session auth on every subsequent request.

Authorization-code exchange, user upsert, and JWT cookie issuance.
  • Redirect URI — GOOGLE_REDIRECT_URI must exactly match an authorized redirect URI configured in the Google Cloud OAuth client. Defaults to http://localhost:8000/auth/google/callback.
  • JWT cookie — name access_token, httpOnly, SameSite=Lax, signed with JWT_SECRET (HS256), payload {"sub": user_id, "exp": ...}. Lifetime is jwt_expire_minutes (default 10080 = 7 days).
  • Every protected route depends on get_current_user (core/auth.py), which reads the cookie, verifies the signature, and returns {"id": user_id} — or raises 401. That's deliberately all it returns; anywhere a display name/email is needed (chat attribution, /auth/me), the full row is re-fetched from users by id rather than trusting extra keys on this dict.
  • Session access is a membership question now, not single ownership — see Session membership & roles below. _require_member/_require_admin (server.py) check this per request; a valid JWT alone doesn't grant access to a session you're not a member of.
Startup requirement auth_module.configure(...) runs at import time in server.py, before the app even starts serving. If JWT_SECRET, GOOGLE_CLIENT_ID, or GOOGLE_CLIENT_SECRET are missing, the process raises ValueError and refuses to start — even for local development. The CLI (main.py) has no such requirement; it never imports server.py.

Session membership & roles

A session is no longer single-owner. chat_sessions.user_id still records who originally created it, but access is governed entirely by the session_members table — a (session_id, user_id, role) row per participant, role being admin or member. The creator is inserted as admin at session creation (POST /api/sessions); every pre-existing session from before this model existed was backfilled the same way, once, by _migrate_membership().

  • Any member (admin or not) can chat, view the roster, and rename the session.
  • Admin-only: inviting/removing members, changing roles, deleting the session, and deciding expense proposals (see below).
  • Last-admin guard — update_member_role/remove_session_member (core/database.py) refuse to demote or remove a session's last remaining admin, raising ValueError (surfaced as HTTP 400). The check and the write are one atomic statement (the admin count is a correlated subquery in the UPDATE/DELETE's own WHERE clause, wrapped in BEGIN IMMEDIATE) rather than a separate SELECT-then-write — a check-then-act split here would let two concurrent demotions both read "2 admins" and both proceed, leaving zero.
  • Invite by email — POST /api/sessions/{id}/members looks the target up by get_user_by_email() (case-insensitive), which only finds someone who has signed in at least once; there's no invite-a-stranger flow. Re-inviting an existing member is an idempotent no-op, not an error — add_session_member does the existence check and insert as one INSERT ... ON CONFLICT DO NOTHING statement for the same check-then-act reason as above.

The agent tool-calling loop

Each session owns one ChatAgent instance. The agent doesn't parse bills or do arithmetic itself — it's an LLM bound to six Python functions ("tools"). Critically, these tools no longer mutate the shared SessionState directly for anything new or changed: SessionState represents only approved data, and every new or edited bill is staged as an expense_proposals row instead, materialized into SessionState/the DB only once an admin approves it (see Expense proposal approval below). calculate_split is the one tool that still reads SessionState directly, since it only ever needs to see approved bills.

One agent.chat() call: rebuild the prompt from live state + pending proposals every turn, let the model call tools, feed results back, repeat.

The six tools

ToolPurpose
add_billParses bill text/items into a draft and stages it as a new expense_proposals row — never appends directly to SessionState.bills.
set_participantsSets the full list of people splitting the bill(s). Names are normalized with .strip().title(). Unchanged by the proposal system — this is session-level metadata, not a bill.
assign_itemsAssigns items to specific people (equal or quantity-based splits, including fractional units). Routes through the pending-proposal-or-correction logic below rather than mutating a bill in place.
mark_items_unassignedMarks items to be split equally across all participants. Same proposal-routing as assign_items.
set_payerRecords who fronted the money for a bill. Same proposal-routing as assign_items.
calculate_splitComputes per-person balances across all approved bills, distributes tax/tip proportionally, generates the minimal settlement, and marks the session finalized. Only tool that reads SessionState directly — nothing here goes through the proposal system.

How a bill-changing tool decides where an edit goes

assign_items, set_payer, and mark_items_unassigned all funnel through the same resolution logic (_load_bill_for_edit / _persist_edit in agents/chat_agent.py) to decide what a given bill_id actually refers to:

  • A still-pending proposal exists for that bill_id (_find_pending_proposal) — the edit mutates that proposal's payload in place via db.update_proposal_payload(). No new approval cycle; it's still the same unreviewed draft.
  • No pending proposal, but an approved bill with that bill_id exists in SessionState — this is a correction. A fresh snapshot of the approved bill is taken, the edit applied to the snapshot, and the result staged as a new expense_proposals row (supersedes_bill_id set to that bill's DB row id at creation time). The original approved bill is untouched until this new proposal is itself approved.
  • Neither — the tool returns a "bill not found" error, listing known bill ids from both approved bills and still-pending proposals (_known_bill_ids), so a bill the model just proposed doesn't vanish from that list before it's approved.

The one subtlety in the correction path: supersedes_bill_id is not trusted at decision time, because its foreign key is ON DELETE SET NULL (needed so the bill delete-and-reinsert on every normal save doesn't violate it) — it routinely goes stale before a proposal is decided, sometimes within the same turn that created it. decide_proposal() re-resolves the real target fresh, by the natural key (session_id, payload["bill_id"]), which is stable across that churn. Whether a given proposal is a correction, for display purposes (e.g. flagging it to an admin reviewing the queue), is likewise computed fresh at read time (is_correction/_is_correction()) rather than read off that same unreliable column.

Speaker attribution

A session can have several real people messaging it, not just one. ChatAgent.chat() takes optional speaker_name/speaker_user_id params — when given, speaker_name is prefixed onto the message content (e.g. "[Alice] we had pizza", see the system prompt's "Group chat" section) so the model can track who said what, and speaker_user_id drives which user a staged proposal is attributed to.

Why this is threaded through RunnableConfig, not stored on self An earlier version stored the current turn's speaker_user_id as a plain attribute on the ChatAgent instance. Since server.py caches one ChatAgent per session and reuses it across requests, two real concurrent senders in the same session could race: whichever request's assignment to that attribute happened last would "win" for both turns' tool calls, misattributing one person's proposal to the other. The fix was to stop storing it on self entirely — speaker_user_id is threaded through LangGraph's own per-invocation RunnableConfig instead (_speaker_user_id(config)), which LangGraph builds fresh for each chat() call and passes down to every tool/node invocation for that call specifically. Verified with forced-interleaving concurrency tests (two real threads, one deliberately stalled mid-call) before and after the fix.

The CLI (main.py) never passes either parameter — with both None, message content is unprefixed and every tool takes its direct, non-proposal-routing branch exactly as it did before the approval system existed. This is deliberate: the CLI has no sessions, no membership, and no admin to approve anything.

max_iterations (default 10, from ChatAgentConfig) bounds how many model calls a single user turn can trigger. If the model keeps calling tools without ever returning plain text within that budget, the agent gives up with a generic "having trouble processing that" reply.

Expense proposal approval workflow

expense_proposals is a staging table — a draft that hasn't affected anyone's balance yet. Its payload column mirrors the shape of a bill (bill_id, description, raw_text, items[], tax, tip, paid_by) as JSON, since it isn't materialized into bills/bill_items until approved.

Created
A bill-changing tool call with no existing approved bill to correct — db.create_proposal(), status pending.
Edited while pending
A further tool call against the same still-pending bill_id — db.update_proposal_payload() overwrites the payload in place; no new row.
Approved
POST /api/sessions/{id}/proposals/{id}/approve (admin only) → decide_proposal(..., "approved") — inserts a new bills row, or (for a correction) updates the existing one and replaces its bill_items, all in one transaction. status becomes approved and can never be decided again.
Rejected
POST .../reject → status becomes rejected; nothing is written to bills/bill_items.

decide_proposal()'s own guard against being decided twice is folded into the UPDATE itself (WHERE id = ? AND status = 'pending', rowcount checked) rather than a prior SELECT — the same check-then-act hazard as the membership guards above: two concurrent decisions on the same proposal could otherwise both observe pending and both proceed, the second hitting the bills table's UNIQUE(session_id, bill_id) constraint. A single UPDATE can't be interleaved with another writer, so exactly one caller ever wins the claim — the other gets a ValueError, surfaced by server.py as HTTP 409 (a conflict with current state, not a missing resource).

Approving/rejecting must evict the cached agent in the same locked step as the DB write approve_proposal/reject_proposal pop the session's entry from server.py's in-memory sessions cache immediately after decide_proposal() succeeds, inside the same with _get_session_lock(session_id): block. Doing the DB write first and evicting afterward (outside the lock, or in a separate locked step) leaves a window where a concurrent chat turn can grab the lock, find the still-cached pre-approval agent, and complete its own write-through save — silently overwriting the just-approved bill with the stale in-memory state. This was a real bug, caught and fixed during testing; eviction now happens atomically with the write that makes it necessary, mirroring how delete_session already combined its DB delete and cache-pop into one locked step.

Concurrency: per-session locking

A session can have multiple real concurrent senders now, so server.py keeps one threading.Lock per session_id (_session_locks, get-or-created via _get_session_lock(), dropped via _drop_session_lock() once a session is deleted so the dict doesn't grow unboundedly over a long-running process).

_run_chat_turn() wraps the entire turn in this lock — agent lookup/construction, agent.chat(), persistence, and the state snapshot returned to the caller — not just the model call. This matters because _get_agent()'s cache-miss path (construct a new ChatAgent, cache it) is itself an unsynchronized check-then-act: two first-touch requests for the same brand-new session could otherwise each build an independent agent/state object before either took the lock, and whichever saved last would silently discard the other's bill. The state snapshot must likewise be read before the lock releases, or a concurrent turn could mutate agent.state in the gap between this turn's unlock and its own serialization.

GET /sessions/{id}/state takes the same lock for the same reason (an unlocked read could race a concurrent mutation, or redundantly construct a second agent on a cache miss). Session deletion and proposal decisions take it too, for the reasons described above.

upload_image needs asyncio.to_thread, not just the lock upload_image is an async def endpoint, but both the vision-model call (analyzer.analyze()) and _run_chat_turn() (which holds a plain, blocking threading.Lock) are synchronous. Calling either directly from the coroutine would block FastAPI's single event-loop thread for their full duration — stalling every request the process is serving, not just this one. Both are run via await asyncio.to_thread(...) so lock contention or a slow vision-model call on one session can't freeze the app for everyone else.

Receipt images

Image upload doesn't bypass the chat agent — it feeds it. POST /sessions/{id}/image sends the uploaded bytes to ImageAnalyzer, which prompts a vision-capable model to classify the image and, if it's a bill, transcribe it to text. That transcription (or a "this isn't a receipt" description) is then wrapped as a synthetic user message and passed straight into the same agent.chat() loop described above — so the model still decides whether to call add_bill, and the result is staged as a proposal exactly like a pasted-text bill would be.

  • The vision request format differs by provider: OpenAI/Google use image_url content blocks (base64 data URI); Anthropic uses its native image content block.
  • The model is asked to return strict JSON (is_bill, description, message, bill_text); markdown code fences are stripped before parsing, and a JSON decode failure is treated as "not a bill" rather than raising.

Session persistence

Conversation memory and bill-splitting state are deliberately kept in two separate systems, each the source of truth for its own half:

  1. The chat conversation itself (every message, tool call, and tool result) lives in LangGraph's own checkpoint tables, managed entirely by core/checkpointer.py's SqliteSaver, keyed by thread_id = session_id. ChatAgent never serializes or restores this by hand — LangGraph's graph.invoke() picks it up transparently on the next call for that thread.
  2. Approved bill-splitting data (SessionState: participants, approved bills/items, finalized) lives in the normalized tables below, written through to SQLite after every turn.
  3. An in-memory cache in server.py — sessions: dict[str, ChatAgent], scoped to the running process, guarded by the per-session locks described above.
Cache hit
Request arrives → session already in the sessions dict → used directly (under the session's lock).
Cache miss
_get_agent() constructs a fresh ChatAgent (its LangGraph graph resumes conversation automatically via the checkpointer) and loads SessionState from the normalized tables via load_session_state()/SessionState.from_dict().
After every turn
_save_agent() → save_session_state() deletes and reinserts participants/bills/bill_items/settlements for the session from the current (approved-only) SessionState. The session is auto-renamed to the first bill's description the moment SessionState.bills grows.
Known gap: auto-rename doesn't fire while a bill is only pending The rename trigger above checks len(state.bills) growing — true before the proposal system existed, when add_bill appended straight to SessionState.bills. Now a new bill only reaches SessionState.bills once an admin approves it, so a session with an unapproved bill sitting pending never gets auto-renamed. Tracked in Testing Feedback as a confirmed regression, not yet fixed.
DB_PATH is required, and the file is never auto-created init_db() (core/database.py) raises ValueError immediately if DB_PATH is unset or empty, and raises FileNotFoundError if it's set but the file doesn't exist yet — neither case falls back to anything. This is deliberate on two counts: DB_PATH is the seam that will later carry a cloud database connection string instead of a local file path, so it shouldn't have an implicit default; and a typo'd path should fail loudly rather than silently standing up a fresh, empty database that looks like data loss the next time you look for your sessions. Both checks run during app startup (the FastAPI lifespan handler), same fail-fast timing as a missing JWT_SECRET.
Provisioning a database schema.sql (repo root) is the single source of truth for the schema — both it and core/database.py read the same file, nothing to keep in sync by hand. scripts/init_db.sh is the one recommended entry point for creating a fresh database: it resolves DB_PATH the same way the app does (explicit env var, else .env), then runs schema.sql through the sqlite3 CLI if it's on PATH, or falls back to the Python sqlite3 module (create_db() in core/database.py) if it isn't — which is the case inside the Docker image, since python:3.11-slim doesn't ship the CLI binary. Both paths are idempotent: re-running against an existing file is a safe no-op, never an overwrite. init_db() (server startup) never creates the file itself — it only verifies it exists, applies schema.sql, and runs three one-time column/table migrations (_migrate_chat_sessions, _migrate_membership, _migrate_expense_proposals_fk) that each check their own preconditions before touching anything, so they're safe to run unconditionally on every startup.
Known limitation The in-memory sessions cache (and its matching _session_locks) is per-process. It's safe under a single uvicorn worker (the default for local dev and the provided Dockerfile). Correctness doesn't depend on it — every request still re-checks membership against SQLite and reloads on a cache miss — but two processes sharing one SQLite file would each keep their own independent in-memory copy of a hot session, uncoordinated with each other.
Dead config ServerConfig.host / ServerConfig.port (in config/defaults.yaml) are loaded but never passed to uvicorn — the app only reads cors_origins from ServerConfig. The actual bind address/port come from however uvicorn is invoked (flags, or its own default of 127.0.0.1:8000; the Dockerfile/compose setup pins it to 0.0.0.0:8000 explicitly). Editing server.port in the YAML has no effect on which port the server listens on.

Docker & docker compose

docker-compose.yml builds from the Dockerfile, loads .env, exposes port 8000, and bind-mounts ./$DB_PATH (host) onto /app/$DB_PATH (container) — volumes: - ./${DB_PATH}:/app/${DB_PATH}, using Compose's own variable substitution against the same .env. That's the only mount; there's no named volume. Because it's a real host file rather than a Docker-managed volume, the database is the same file whether you run uvicorn locally or in the container, visible and inspectable directly from the repo root — and it's why DB_PATH must be a relative path: Compose's short volume syntax treats a bare relative name as a named-volume reference unless prefixed with ./, and that prefix only makes sense for a relative path. This also means docker compose run --rm splitpro ./scripts/init_db.sh must run before the mount is attempted — Docker creates an empty directory at a bind-mount source that doesn't exist yet, on both the host and the container side, rather than erroring, so provisioning genuinely has to happen first. The image runs as a non-root user; both the Dockerfile's HEALTHCHECK and the compose file's healthcheck: poll GET /health. The container still refuses to boot without JWT_SECRET, GOOGLE_CLIENT_ID, and GOOGLE_CLIENT_SECRET in .env, same as running locally.

Data model

The in-memory Python model below represents only approved session state — it has no knowledge of pending proposals, which live purely as JSON payloads in the DB until decided.

One session → many approved bills → many line items. All dataclasses, all JSON-serializable. bill_id is a random token (bill_<8 hex chars>), not sequential — so a deleted bill's id can never be reassigned to an unrelated one.
  • shared — cost of the item splits equally among everyone in assigned_to.
  • unassigned — set by mark_items_unassigned; splits equally across all participants, not just assigned_to.
  • qty_allocations — maps a person to the (possibly fractional) number of units of that item they consumed, at unit_price = price / qty each. Any unallocated remainder is split equally among the remaining people in assigned_to (or all participants, if none remain).

Membership & proposal tables

These two tables exist only at the DB level — nothing in SessionState mirrors them.

TableShape
session_members(session_id, user_id, role, joined_at), unique per (session_id, user_id). role is admin or member.
expense_proposals(session_id, proposed_by, status, supersedes_bill_id, payload, decided_by, decided_at). status is pending / approved / rejected; payload is the draft bill as JSON.

Settlement algorithm

Run by calculate_split (and mirrored by _compute_settlement in server.py for the live state view) — over approved bills only. For each bill:

  1. For every item, compute each assigned person's share:
    • If qty_allocations is set: unit_price × units consumed per person, plus an equal split of any unallocated units among the rest of assigned_to.
    • Otherwise: the item price split evenly across assigned_to (or all participants, if the item was never assigned — this also raises a warning surfaced in the final report).
  2. Distribute tax + tip across people proportionally to their subtotal share of that bill (not split evenly) — person_share += (person_subtotal / bill_subtotal) × (tax + tip). If the bill subtotal is zero, tax/tip splits evenly instead.
  3. Accumulate into one global balance map across all approved bills in the session: the bill's payer is credited the full bill total; every participant (including the payer) is debited their computed share.

Debt minimization

Settlement.generate_settlements() takes the final balance map and greedily matches the largest creditor against the largest debtor, repeatedly, until all balances are zeroed (a threshold of ±$0.001 absorbs floating-point noise). This is a fast heuristic for reducing the number of payments — not a proof-of-optimality algorithm — but it's exact for the common small-group cases SplitPro targets. 

while creditors and debtors:
    take largest creditor, largest debtor
    settle min(creditor_amount, debtor_amount) between them
    whichever hits zero first drops out of its list; continue

Frontend

A single-page app with no build step or framework — frontend/index.html, app.js, and style.css, served directly by FastAPI's StaticFiles mount at / (mounted after all API routes, so API paths always take precedence over static files).

  • Auth gate — on load, app.js calls GET /auth/me; a failure shows the Google sign-in overlay, success shows the app shell.
  • Session sidebar — lists sessions from GET /api/sessions (now every session the user is a member of, not just ones they created); the last-opened session id is cached in localStorage and restored on reload.
  • Chat panel — a real group chat: messages render with sender attribution (resolved against the member list from GET /api/sessions/{id}/members, since chat_messages only stores a raw user_id), and posts to /sessions/{id}/chat or /sessions/{id}/image.
  • State panel — renders the serialized SessionState: bills, items, assignments, a pending-proposals count, and the settlement once finalized is true.
  • Members tab — roster with roles; admins get invite-by-email and promote/demote/remove controls, non-admins see the same list read-only.
  • Approvals tab (admin-only) — lists pending proposals as bill-style cards, each with Approve/Reject wired to the corresponding endpoint; a correction proposal is flagged distinctly from a brand-new bill via is_correction.
Serialized state ≠ full model The JSON the server sends to the browser (_serialize_state in server.py) is a simplified view — each item exposes name, price, assigned_to, and shared, but not qty or qty_allocations. Quantity-based splits are fully tracked and priced correctly server-side; the frontend just doesn't render the per-person unit breakdown. pending_proposals_count is included so the chat UI can show a badge without a second round-trip — it's a bare COUNT(*), not the full proposal list/detail (that comes from GET /api/sessions/{id}/proposals, admin-only).
