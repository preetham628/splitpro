Architecture

How a chat message becomes a settled bill: auth, the agent's tool-calling loop, persistence, and the settlement math.

Authentication

SplitPro uses Google OAuth (authorization-code flow) for sign-in, and its own signed JWT in an httpOnly cookie for session auth on every subsequent request.

Authorization-code exchange, user upsert, and JWT cookie issuance.
  • Redirect URI — GOOGLE_REDIRECT_URI must exactly match an authorized redirect URI configured in the Google Cloud OAuth client. Defaults to http://localhost:8000/auth/google/callback.
  • JWT cookie — name access_token, httpOnly, SameSite=Lax, signed with JWT_SECRET (HS256), payload {"sub": user_id, "exp": ...}. Lifetime is jwt_expire_minutes (default 10080 = 7 days).
  • Every protected route depends on get_current_user (core/auth.py), which reads the cookie, verifies the signature, and returns {"id": user_id} — or raises 401.
  • Session ownership is checked separately per request via db.session_belongs_to_user(session_id, user_id) — a valid JWT alone doesn't grant access to another user's session.
Startup requirement auth_module.configure(...) runs at import time in server.py, before the app even starts serving. If JWT_SECRET, GOOGLE_CLIENT_ID, or GOOGLE_CLIENT_SECRET are missing, the process raises ValueError and refuses to start — even for local development. The CLI (main.py) has no such requirement; it never imports server.py.

The agent tool-calling loop

Each session owns one ChatAgent instance. The agent doesn't parse bills or do arithmetic itself — it's an LLM bound to six Python functions ("tools") that read and write one shared SessionState object. The LLM decides which tools to call and with what arguments; the tools are the only thing allowed to mutate state.

One agent.chat() call: rebuild the prompt from live state every turn, let the model call tools, feed results back, repeat.

The six tools

ToolPurpose
add_billParses bill text/items the user provided into a new ParsedBill (line items, tax, tip). Called once per bill.
set_participantsSets the full list of people splitting the bill(s). Names are normalized with .strip().title().
assign_itemsAssigns items to specific people. Supports equal splits and quantity-based splits (e.g. "Alice had 1 of 4 burgers", including fractional units) via qty_per_person.
mark_items_unassignedMarks items to be split equally across all participants (e.g. "just split the appetizer evenly").
set_payerRecords who fronted the money for a given bill.
calculate_splitComputes per-person balances across all bills, distributes tax/tip proportionally, and generates the minimal settlement — then marks the session finalized.

The tools are closures built over one live SessionState instance (_build_tools(state) in agents/chat_agent.py) — they're rebuilt every time an agent is restored from the database so they close over the freshly-deserialized state, not a stale one.

max_iterations (default 10, from ChatAgentConfig) bounds how many model calls a single user turn can trigger. If the model keeps calling tools without ever returning plain text within that budget, the agent gives up with a generic "having trouble processing that" reply.

Receipt images

Image upload doesn't bypass the chat agent — it feeds it. POST /sessions/{id}/image sends the uploaded bytes to ImageAnalyzer, which prompts a vision-capable model to classify the image and, if it's a bill, transcribe it to text. That transcription (or a "this isn't a receipt" description) is then wrapped as a synthetic user message and passed straight into the same agent.chat() loop described above — so the model still decides whether to call add_bill.

  • The vision request format differs by provider: OpenAI/Google use image_url content blocks (base64 data URI); Anthropic uses its native image content block.
  • The model is asked to return strict JSON (is_bill, description, message, bill_text); markdown code fences are stripped before parsing, and a JSON decode failure is treated as "not a bill" rather than raising.

Session persistence

Session state lives in three places at once, kept in sync on a write-through basis:

  1. In the ChatAgent object itself — message_history (LangChain messages) and state (SessionState).
  2. An in-memory cache in server.py — sessions: dict[str, ChatAgent], scoped to the running process.
  3. SQLite — the chat_sessions table stores message_history and session_state as JSON text blobs, source of truth across restarts. File location is DB_PATH (env var) — init_db() creates any missing parent directory automatically.
Cache hit
Request arrives → session already in the sessions dict → used directly.
Cache miss
_get_agent() loads the row from SQLite, rebuilds the agent with ChatAgent.from_dict() (using messages_from_dict for history and SessionState.from_dict for state), and re-caches it.
After every turn
_save_agent() serializes the agent back to JSON and writes it to the chat_sessions row (updated_at is bumped). The session is also auto-renamed to the first bill's description the moment a bill is added.
DB_PATH is required, and the file is never auto-created init_db() (core/database.py) raises ValueError immediately if DB_PATH is unset or empty, and raises FileNotFoundError if it's set but the file doesn't exist yet — neither case falls back to anything. This is deliberate on two counts: DB_PATH is the seam that will later carry a cloud database connection string instead of a local file path, so it shouldn't have an implicit default; and a typo'd path should fail loudly rather than silently standing up a fresh, empty database that looks like data loss the next time you look for your sessions. Both checks run during app startup (the FastAPI lifespan handler), same fail-fast timing as a missing JWT_SECRET.
Provisioning a database schema.sql (repo root) is the single source of truth for the schema — both it and core/database.py read the same file, nothing to keep in sync by hand. scripts/init_db.sh is the one recommended entry point for creating a fresh database: it resolves DB_PATH the same way the app does (explicit env var, else .env), then runs schema.sql through the sqlite3 CLI if it's on PATH, or falls back to the Python sqlite3 module (create_db() in core/database.py) if it isn't — which is the case inside the Docker image, since python:3.11-slim doesn't ship the CLI binary. Both paths are idempotent: re-running against an existing file is a safe no-op, never an overwrite. init_db() (server startup) never creates anything itself — it only verifies the file exists and ensures the schema is current on it.
Known limitation The in-memory sessions cache is per-process. It's safe under a single uvicorn worker (the default for local dev and the provided Dockerfile). Correctness doesn't depend on it — every request still re-checks ownership against SQLite and reloads on a cache miss — but two processes sharing one SQLite file will each keep their own independent in-memory copy of a hot session, so the fastest write wins rather than being coordinated.
Dead config ServerConfig.host / ServerConfig.port (in config/defaults.yaml) are loaded but never passed to uvicorn — the app only reads cors_origins from ServerConfig. The actual bind address/port come from however uvicorn is invoked (flags, or its own default of 127.0.0.1:8000; the Dockerfile/compose setup pins it to 0.0.0.0:8000 explicitly). Editing server.port in the YAML has no effect on which port the server listens on.

Docker & docker compose

docker-compose.yml builds from the Dockerfile, loads .env, exposes port 8000, and bind-mounts ./$DB_PATH (host) onto /app/$DB_PATH (container) — volumes: - ./${DB_PATH}:/app/${DB_PATH}, using Compose's own variable substitution against the same .env. That's the only mount; there's no named volume. Because it's a real host file rather than a Docker-managed volume, the database is the same file whether you run uvicorn locally or in the container, visible and inspectable directly from the repo root — and it's why DB_PATH must be a relative path: Compose's short volume syntax treats a bare relative name as a named-volume reference unless prefixed with ./, and that prefix only makes sense for a relative path. This also means docker compose run --rm splitpro ./scripts/init_db.sh must run before the mount is attempted — Docker creates an empty directory at a bind-mount source that doesn't exist yet, on both the host and the container side, rather than erroring, so provisioning genuinely has to happen first. The image runs as a non-root user; both the Dockerfile's HEALTHCHECK and the compose file's healthcheck: poll GET /health. The container still refuses to boot without JWT_SECRET, GOOGLE_CLIENT_ID, and GOOGLE_CLIENT_SECRET in .env, same as running locally.

Data model

One session → many bills → many line items. All dataclasses, all JSON-serializable.
  • shared — cost of the item splits equally among everyone in assigned_to.
  • unassigned — set by mark_items_unassigned; splits equally across all participants, not just assigned_to.
  • qty_allocations — maps a person to the (possibly fractional) number of units of that item they consumed, at unit_price = price / qty each. Any unallocated remainder is split equally among the remaining people in assigned_to (or all participants, if none remain).

Settlement algorithm

Run by calculate_split (and mirrored by _compute_settlement in server.py for the live state view). For each bill:

  1. For every item, compute each assigned person's share:
    • If qty_allocations is set: unit_price × units consumed per person, plus an equal split of any unallocated units among the rest of assigned_to.
    • Otherwise: the item price split evenly across assigned_to (or all participants, if the item was never assigned — this also raises a warning surfaced in the final report).
  2. Distribute tax + tip across people proportionally to their subtotal share of that bill (not split evenly) — person_share += (person_subtotal / bill_subtotal) × (tax + tip). If the bill subtotal is zero, tax/tip splits evenly instead.
  3. Accumulate into one global balance map across all bills in the session: the bill's payer is credited the full bill total; every participant (including the payer) is debited their computed share.

Debt minimization

Settlement.generate_settlements() takes the final balance map and greedily matches the largest creditor against the largest debtor, repeatedly, until all balances are zeroed (a threshold of ±$0.001 absorbs floating-point noise). This is a fast heuristic for reducing the number of payments — not a proof-of-optimality algorithm — but it's exact for the common small-group cases SplitPro targets. 

while creditors and debtors:
    take largest creditor, largest debtor
    settle min(creditor_amount, debtor_amount) between them
    whichever hits zero first drops out of its list; continue

Frontend

A single-page app with no build step or framework — frontend/index.html, app.js, and style.css, served directly by FastAPI's StaticFiles mount at / (mounted after all API routes, so API paths always take precedence over static files).

  • Auth gate — on load, app.js calls GET /auth/me; a failure shows the Google sign-in overlay, success shows the app shell.
  • Session sidebar — lists sessions from GET /api/sessions; the last-opened session id is cached in localStorage and restored on reload.
  • Chat panel — posts to /sessions/{id}/chat or /sessions/{id}/image, renders the agent's reply (via the marked markdown library, loaded from a CDN) and the returned state.
  • State panel — renders the serialized SessionState returned with every chat/image response: bills, items, assignments, and the settlement once finalized is true.
Serialized state ≠ full model The JSON the server sends to the browser (_serialize_state in server.py) is a simplified view — each item exposes name, price, assigned_to, and shared, but not qty or qty_allocations. Quantity-based splits are fully tracked and priced correctly server-side; the frontend just doesn't render the per-person unit breakdown.
