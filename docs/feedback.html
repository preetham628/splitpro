#1Decided — approach

Real-time multi-user chat (no reload required)

Problem: when multiple people are in the same session, nobody sees a new message/state change until they manually reload. No push mechanism exists today — the frontend only fetches on its own actions (loadSession, sendToAgent, etc.).

Research — how WhatsApp / Discord / Telegram do this

All three converge on the same core primitive at scale: a persistent connection (WebSocket, or a custom protocol like MQTT) held open per client, a server-side registry mapping user/session → active connections, and a fan-out dispatcher that pushes a new message to every connection subscribed to that conversation. Presence ("online", "typing…") rides over the same socket as a separate event type. At Discord's scale this means ~8M concurrent WebSocket connections spread across 1000+ regional gateway nodes, with Redis holding the connection-location mapping so any server can route a message to the right gateway.

None of the sharding/Redis-routing machinery is relevant here — that solves "which of our 10,000 servers is this user connected to," and SplitPro runs one process. The applicable part is just: WebSocket connection + in-process fan-out, scoped per session_id — the same shape as the existing sessions in-memory cache dict, just mapping to live sockets instead of ChatAgent instances.

Recommendation

A FastAPI WebSocket endpoint per session (/ws/sessions/{id}), authenticated the same way as the REST endpoints (JWT cookie read during the WS handshake), holding a small dict[session_id, list[WebSocket]] registry. When _run_chat_turn or a proposal decision changes session state, broadcast the new message/state to every open socket for that session. No Redis, no offline queue, no presence/typing needed for v1 — reconnection on page load already gets a client caught up via the existing REST fetch, so the socket only needs to cover "while you're actively looking at the screen."

Sources: Discord Real-Time Infrastructure — WebSocket Gateways, System Design: WhatsApp-like Messaging Service, WebSockets with FastAPI — Build a Real-Time Chat App

#2Decided

Multiple payers on one bill

Problem: bills.paid_by is a single name — can't represent two or more people splitting payment for the same bill.

Decision

paid_by becomes a map (person → amount), not a string. See #3 below — this should be designed together with percentage/share splitting rather than as a separate mechanism, since a bill may need both multiple payers and a non-equal split among them at once.

#3Decided — scope

Percentage / share / absolute-amount splitting — payer side and item side

Problem: need to support three entry modes for who paid and who consumed: equal split, percentage (73% / 20% / 7%), and a direct absolute figure (out of ₹3000: ₹1200 Sumit, ₹1800 me).

Scope agreed

These three entry modes all resolve to the same underlying representation — an amount per person — so the schema only needs one shape: a person → amount contribution map, used identically for payer allocation (replacing the single paid_by string, per #2) and item consumption (extending today's qty_allocations pattern for items). Percentage and equal-split are just convenience input modes that get converted to amounts at entry time — equal = total/n, percentage = total×pct — so the settlement math never needs to know which mode was used, only the resulting amounts. The design work still needed: the exact tool interface (how the agent expresses "percentage" vs "amount" vs "equal" when calling assign_items/set_payer) and validation (contributions must sum to the bill/item total within the existing epsilon tolerance).

#4Decided — light touch only

Prompt quality / item categorization errors

Problem: the agent sometimes merges distinct items under one umbrella name (e.g. lumping whiskey into "beer" when the user said "we split beer"). Reported as happening in more than one tested scenario, not a one-off.

Decided scope

The draft use-case list (restaurant/bar tabs, groceries, trips, rent/utilities, event pooling, work lunches) is good enough as-is — no further brainstorming needed. Fix: a small, targeted prompt tweak aimed specifically at the categorization failure (don't merge distinct named items under one umbrella name), not a broad rewrite. Outside of this one failure mode the current prompt is working well and shouldn't be disturbed.

#5Deferred — future release

Agent replies too eagerly in group chat

Problem: the agent responds after every single message, even casual back-and-forth between participants that isn't directed at it. Should be smarter about when to actually speak up.

This is the "when should the agent even speak" question from the original multi-user design discussion — deferred then in favor of the approval system as the safety net, and still a visible problem on its own regardless of the approval flow. Pushed to a future release rather than this one — not forgotten, just not blocking the current batch of work.

#6Decided

Settlement doesn't reflect a late correction after finalization

Problem: after a session is finalized, telling the agent about an additional late payment gets a conversational "here's your updated settlement…" reply in chat, but the sessions page never changes, and there's no approval request raised for it.

Agreed direction

Settlement isn't an action the agent performs — it's a property of whatever bill data currently exists. The agent already has full write access to bills/items/payers through the proposal system; settlement doesn't need its own write path on top of that. So:

  • calculate_split stops being a "finalize" action and becomes a pure report — compute balances from whatever's currently approved, print them, done. No flag gets set, nothing gets locked.
  • The finalized flag's current job — gating whether /state even returns a settlement — goes away. Settlement always reflects current approved-bill data, live, the same way the underlying balance computation already works today.
  • The frontend's settlement card shows whenever there's valid data to compute from, not behind a "someone finalized this" condition.

This closes #6 structurally rather than patching it — once there's no gated/cached settlement state to fall out of sync, there's nothing left for a correction to desynchronize from. Every read is the current truth, whether it comes from chat or the sessions page.

Resolved

No "closing"/archiving a session for now — finalized is dropped entirely, sessions stay perpetually live and editable. A manual "mark this session as settled/closed" action is noted as a possible future feature (ties to the main roadmap's partial-settlements/session-lifecycle ideas) but deliberately out of scope here.

#8Decided — scope, patterns noted below

UI: panel toggle, responsive sizing, name overflow

Problem: need a way to toggle the chat-session and approval side panels, the layout needs to auto-size for phones, and some participant names overflow the bill card's boundary.

Patterns worth following (standard, well-established)
  • Collapsible drawer sidebar — the Discord/Slack/WhatsApp Web pattern: sidebar slides in/out via a hamburger toggle, full-screen overlay on narrow viewports instead of a permanent column
  • Responsive breakpoint — below a phone-width threshold, panels stack instead of sitting side-by-side; only one panel visible at a time, switched via tab/toggle
  • Name overflow — likely a missing min-width: 0 on a flex child plus text-overflow: ellipsis/white-space: nowrap, with the full name available via a title tooltip attribute on hover

No open design questions here — straightforward frontend work once scoped.

#9Confirmed bug + decided UX direction

Chat title stuck at "New Session"; no title bar above the chat

Problem: the title area above the chat panel is blank — the session name only shows in the left sidebar — and it stays "New Session" even after an active multi-user conversation.

Confirmed root cause

The auto-rename trigger in server.py checks len(state.bills) growing — true before the proposal system existed, but add_bill now only creates a pending proposal and doesn't touch state.bills until an admin approves it. In any session with an unapproved bill sitting pending, the rename condition never fires. Straightforward regression from the Task 3 refactor, not a missing feature.

Decided UX direction

WhatsApp-style: a small top bar above the chat panel showing the current session's title (currently blank/absent), with two user-facing options — manually rename it, or toggle auto-generated naming as the conversation progresses. Worth upgrading the auto-name logic at the same time: rather than just reusing the first bill's description, generate the title from actual conversation content (and re-trigger it off proposal creation, not just approval, to also fix the root bug above).

#10Decided

Long multi-user conversations — context window handling

Problem: unclear how the system behaves once a group chat runs long.

Confirmed — there was nothing here

Every turn sends the entire accumulated message history to the LLM, completely unwindowed, forever. Fine for a short single-user session; a real cost/latency/context-limit problem for a long-running group chat.

Decided design — sliding window + background summarization

Key reassurance that shaped the final numbers: the actual financial data (bills, items, assignments, payers) is never derived from chat history — it's rebuilt fresh from the database into the system prompt on every turn via state.state_summary(). So the conversation history is only load-bearing for short-term dialogue coherence (resolving "the dolphins bill", recent back-and-forth), never for financial correctness. That means the window can be small and summarization can be reasonably aggressive without real risk.

  • Unit of counting: "rounds," not raw messages. A round = one human message plus everything the agent did in response to it (however many tool calls that took). Triggering off raw message count was rejected — tool-call-heavy activity from a busy multi-user session would inflate the raw count fast and trigger summarization constantly, compounding lossy summaries on top of each other for no good reason. Counting rounds ties the trigger to actual conversational volume instead.
  • Window: 8 rounds kept verbatim.
  • Once exceeded: summarize the oldest 4 rounds, keep the newest 4, folding the oldest into a running summary rather than discarding it outright.
  • Safety net: an independent raw-message ceiling (~40 messages) that can trigger summarization early regardless of round count, for the edge case where a single round is enormous (e.g. a giant pasted bill generating dozens of tool calls in one exchange).
  • Cut points are round-aligned, which also guarantees a tool-call and its matching tool-response are never split across the summarized/kept boundary.
  • Storage: a new context_summary column on chat_sessions, injected into the system prompt the same way _pending_proposals_summary() already is — invisible to users, purely internal.
  • Model: reuse the session's already-configured chat model, no new provider config.
Fire-and-forget, no latency impact — confirmed design requirement

Runs via FastAPI's BackgroundTasks, which executes only after the triggering request's HTTP response has already been sent — the person whose message crossed the threshold gets their normal reply with zero added wait. For concurrent users in the same session while summarization runs: the slow part (the LLM call that generates the summary) happens without holding the per-session lock, working off a snapshot of the messages to compress. The lock is only acquired briefly at the end, to persist the finished summary and remove the now-redundant messages from the checkpoint — a fast operation, not a multi-second LLM round-trip — so a concurrent request is never meaningfully blocked by a background summarization run in progress.

#11Decided

Missing tools: remove bill, rename bill, add/remove items on an existing bill

Problem: editing items on an already-approved bill works (via the correction-proposal flow), but there's no way to remove a whole bill, rename one, or add/remove a single item from one.

Decided

All three (remove bill, rename bill, add/remove item) go through the same correction-proposal/approval cycle as every other edit — no separate mechanism. These three tools are enough for now; the other candidate tools floated earlier (list/summarize, merge bills, partial-payment tracking, undo-proposal, categorization/tagging) aren't needed yet — left for a future pass if they come up again.
