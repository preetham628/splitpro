Future scope

Three directions the app could evolve in, each grounded in a gap the current implementation already documents. This is a planning doc, not a commitment — nothing here is built yet.

Feature depth Multi-user collaboration Production readiness
Current focus Multi-user collaboration is the active track. Production readiness is deliberately deferred.

A. Feature depth (Splitwise-like)

Ongoing ledgers, recurring expenses, multi-currency, and reporting — depth within a single user's use of the app, no new collaboration model required.

#RequirementWhy it's a jump from todayEffort
A1 Running balances across sessions Today bills/settlements are scoped to one chat_sessions row with no cross-session ledger; needs a new ledger_entries table keyed by (payer, ower) independent of session. L
A2 Recurring / templated bills No template concept exists; needs a schedule model plus a way to re-trigger the agent flow without a human re-pasting text. M
A3 Multi-currency No currency field anywhere in bills/bill_items/settlements; needs a currency column plus conversion handling in core/settlement.py. M
A4 Partial / marked-paid settlements settlements is fully rewritten on every finalize; needs a payment-status sub-ledger, not just a computed list. M
A5 Edit/undo a finalized session Today only supports "add more bills and recalculate from scratch" — no partial edit path. S–M
A6 Categories / export (CSV, monthly summary) Purely additive, no architectural conflict. S
A7 Receipt retention / re-view Images live inline as base64 in chat_messages.image_base64 for transcript replay only — no dedicated gallery. S
Dependency A1 (cross-session ledger) reshapes the data model the most — worth deciding early, since A4 and A6 are far cheaper to build on top of it than to retrofit later.

B. Multi-user collaboration active track

Real accounts for participants, shared sessions, invites, notifications — turning single-owner sessions into something a group actually shares.

#RequirementWhy it's a jump from todayEffort
B1 Participants as real accounts, not free-text names session_participants.name is a plain string, unique per session, with no link to users.id. Foundational — everything else here depends on it. L
B2 Invite flow (email or link) to add a real user to a session Needs B1 first; needs an invite / pending-membership state machine. M (after B1)
B3 Shared session ownership — more than one user can view/edit a session chat_sessions.user_id is a single FK today (session ownership is checked and enforced as single-owner); needs a join table (session_members) and a rework of every ownership check in server.py. M (after B1)
B4 Notifications (email/push) on bill added, split finalized, payment marked No notification infra exists today — needs a delivery mechanism plus an events/outbox table. M
B5 Activity feed / audit trail per session chat_messages is conversational, not structured; would want a separate session_events table ("Alice added Item X"). S–M
B6 Permissions model (who can finalize, who can edit others' assignments) Currently anyone with session access can call any tool; needs a role concept once B3 exists. S (after B3)
Dependency B1 is the linchpin — the largest single change (touches auth, schema, and every tool in agents/chat_agent.py that currently takes a free-text name), but B2–B6 are all comparatively small once it's done.

C. Production readiness deferred

Hardening what exists — cloud DB, scaling, tests, observability — rather than adding features. Parked for now.

#RequirementWhy it's a jump from todayEffort
C1 Cloud/managed database (Postgres, etc.) DB_PATH is explicitly a placeholder seam, but core/database.py and core/checkpointer.py both currently assume raw SQLite file semantics (journal mode forced to DELETE, SqliteSaver). M–L
C2 Horizontal scaling (multiple app instances) Blocked on C1 — the in-memory session cache and LangGraph's SQLite checkpointer are both single-file, single-process by construction. L (after C1)
C3 Automated test suite Zero test files exist today; highest-leverage, lowest-risk item on the whole roadmap. M, do first
C4 Structured logging / observability (LLM call tracing, latency, cost per session) Only ad hoc stderr prints exist today; no visibility into LLM spend or failure rates. S–M
C5 Rate limiting / abuse protection Every chat/image call costs real LLM money with zero throttling today. S
C6 Secrets management (not flat .env in prod) Fine for local dev/Docker Compose; a real deploy needs a secrets manager or platform-level env injection. S
C7 CI/CD pipeline Depends on C3 existing to be worth anything. S (after C3)

Cross-cutting sequencing

C3 underlies every track. B1 gates the rest of the collaboration track. C1 gates scaling. A1 gates the cheaper ledger-dependent features.

Product-first path: C3 → B1 → C1 → (A1 or B2/B3) → C2. Personal-use path: C3 → A1 → A2/A4/A6, skipping the collaboration track entirely.
