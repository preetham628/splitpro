TASK 6Ready now

Data layer: multi-payer + flexible split model

Addresses feedback items #2 and #3. Depends on nothing.

Workflow: branch off multi-user (git checkout -b task6-split-model-data-layer multi-user). Commit incrementally with meaningful messages. Open the PR against multi-user, not main.
Context

Today, bills.paid_by is a single TEXT name — can't represent two people splitting payment. bill_items.qty_allocations is a JSON dict of person → fractional units, only meaningful when an item's qty > 1. Neither supports percentage-of-total or a direct absolute-amount entry.

Decided design

Unify both sides to a single canonical shape: a dollar-amount-per-person contribution map, used identically for who paid and who owes for an item. Percentage, equal-split, and "N of M units" are input conveniences that resolve to amounts at the tool-call layer (Task 7) — this task only needs to store and persist the resulting map, not convert between modes.

Changes — schema.sql
  • bills.paid_by keeps its column but changes meaning: now stores JSON like {"Alice": 1800.0, "Sumit": 1200.0} instead of a plain name string.
  • bill_items.qty_allocations → add a new column cost_allocations TEXT NOT NULL DEFAULT '{}' storing dollar amounts per person ({"Alice": 8.00, "Bob": 4.00}), not fractional units. Migrate existing qty_allocations data into it (amount = units × item.price / item.qty), then drop the old column — this project already has precedent for a clean column drop (_migrate_chat_sessions drops session_state/message_history the same way), reuse that pattern.
Changes — core/database.py
  • New migration function (follow the exact idempotent, check-columns-first pattern already used by _migrate_chat_sessions/_migrate_membership/_migrate_expense_proposals_fk): convert any existing plain-string bills.paid_by value into {"<name>": <bill total>} (preserves old single-payer behavior for bills that already exist); convert qty_allocations → cost_allocations as described above; leave NULL/empty untouched.
  • save_session_state / load_session_state: update to json.dumps/json.loads the new map shapes for both fields.
  • decide_proposal's materialization path (_insert_bill_items, the bills INSERT/UPDATE): same JSON handling — proposal payloads carry the identical shape.
  • Add validate_contribution_map(amounts: dict, total: float, epsilon: float = 0.001) -> bool — checks sum(amounts.values()) is within epsilon of total. Belongs here as a data-integrity concern; Task 7 will call it from the tool layer.
Changes — core/session_state.py
  • ParsedBill.paid_by: Optional[str] → paid_by: Dict[str, float] = field(default_factory=dict). Empty dict replaces None as "not set yet."
  • LineItem.qty_allocations → rename to cost_allocations: Dict[str, float] (dollar amounts). Keep the unit_price property for display purposes even though allocation math no longer uses it directly.
  • from_dict and state_summary(): update to the new shapes. state_summary() specifically needs to render these clearly for the LLM — e.g. paid_by={Alice: $1800.00, Sumit: $1200.00} instead of paid_by=Alice.
  • SessionState.all_bills_ready(): change b.paid_by is not None to bool(b.paid_by).
Acceptance / manual test
  • Fresh DB: create a bill with a multi-payer paid_by map, save, reload, confirm it round-trips correctly.
  • Hand-construct an old-shape DB (string paid_by, populated qty_allocations), run the migration, confirm correct conversion of both fields.
  • Run pytest tests/test_database.py tests/test_session_state.py specifically — these two files test exactly this layer and should pass cleanly.
  • Expected, not a problem: tests/test_chat_agent.py and tests/test_server.py will fail after this change, since they reference the old field names/shapes. That's exactly what Task 7 fixes — don't try to fix those tests in this task.
Non-goals

No agent tool changes, no settlement math changes (both Task 7). No frontend changes (Task 8). Don't touch agents/chat_agent.py or core/settlement.py.

TASK 9Ready now

New tools: remove bill, rename bill, add/remove item

Addresses feedback item #11. Depends on nothing.

Workflow: branch off multi-user (git checkout -b task9-bill-edit-tools multi-user). Commit incrementally with meaningful messages. Open the PR against multi-user, not main.
Context

Editing items on an already-approved bill already works via the correction-proposal flow (assign_items/set_payer detect the target is approved and route a correction through create_proposal(..., supersedes_bill_id=...)). What's missing: removing a whole bill, renaming one, and adding/removing a single item. Decided: all four go through the same approval cycle as every other edit — no separate mechanism.

Key design insight — most of this needs no new backend semantics

rename_bill, add_item_to_bill, and remove_item_from_bill are all just "build a modified full-bill snapshot, submit it as a correction" — exactly what set_payer already does today. They reuse the existing mechanism completely unchanged. Only removing an entire bill needs new materialization logic, since decide_proposal today only knows how to insert-or-update a bill, never delete one.

Changes — core/database.py
  • decide_proposal: support a deletion-flavored proposal. Convention: the payload carries {"action": "remove_bill", "bill_id": "..."} as its entire shape when it represents a removal (no items/tax/tip/paid_by needed). Default all existing/other proposals to an implicit payload.get("action", "upsert") for backward compatibility — every proposal created before this task has no action key.
  • On approval of a remove_bill proposal: resolve the target bill by (session_id, payload["bill_id"]) — the same natural-key resolution already used for every other correction, not by trusting supersedes_bill_id's FK value, for the same staleness reasons already documented on decide_proposal. Then DELETE FROM bill_items WHERE bill_id = ? followed by DELETE FROM bills WHERE id = ?. If no matching bill exists, raise ValueError — same as the existing "not found" handling elsewhere in this function.
  • create_proposal needs no change — it already accepts an arbitrary payload dict.
Changes — agents/chat_agent.py

Four new tools, registered in _build_tools's returned list, documented in SYSTEM_PROMPT_TEMPLATE:

  • remove_bill(bill_id: str) -> str — resolve bill_id against pending proposals first (reuse _find_pending_proposal), then approved bills (state.get_bill). If the target is only a still-pending proposal (never approved), just reject it directly via db.decide_proposal(..., "rejected") — there's nothing real to "remove" yet, creating a removal-proposal for something not yet materialized would be nonsensical. If the target is an already-approved bill, build the {"action": "remove_bill", ...} payload and submit it as a correction proposal, same pattern as every other correction.
  • rename_bill(bill_id: str, new_description: str) -> str — build a full snapshot of the target bill with only description changed, route through the existing correction mechanism exactly like set_payer does.
  • add_item_to_bill(bill_id: str, item: dict) -> str — build a modified snapshot with the new item appended to items[], route through the existing mechanism.
  • remove_item_from_bill(bill_id: str, item_name: str) -> str — fuzzy-match item_name using the same matching logic assign_items already uses, build a modified snapshot with that item removed from items[], route through the existing mechanism.
Acceptance / manual test
  • Remove an approved bill → confirm it disappears from bills only after an admin approves the removal proposal.
  • Remove a still-pending (unapproved) proposal → confirm it's rejected directly, with no second approval cycle needed.
  • Rename an approved bill → confirm only description changes, everything else (items, assignments, payer) survives untouched.
  • Add an item to, and remove an item from, an approved bill → confirm the bill's other items/ assignments are unaffected.
Non-goals

No other brainstormed future tools (list/summarize, merge bills, partial-payment tracking, undo-proposal, categorization) — deferred per the feedback doc. No required frontend changes, though note as a possible follow-up: a removal proposal's payload has no items key, so renderProposals() in frontend/app.js should defensively guard against that shape rather than crash — worth a quick check, not a blocking requirement for this task.

TASK 10Ready now

Sliding window + background conversation summarization

Addresses feedback item #10. Depends on nothing.

Workflow: branch off multi-user (git checkout -b task10-context-window multi-user). Commit incrementally with meaningful messages. Open the PR against multi-user, not main.
Context

Every turn currently sends the entire accumulated LangGraph message history to the LLM, unwindowed, forever — confirmed by reading ChatAgent._agent_node in agents/chat_agent.py. Fine for a short session, a real cost/latency/context-limit problem for a long-running group chat.

Decided design

Important framing that shaped these numbers: the actual financial data (bills, items, assignments) is never derived from chat history — it's rebuilt fresh from the database into the system prompt on every turn via state.state_summary(). So conversation history is only load-bearing for short-term dialogue coherence, never for financial correctness. The window can be small and summarization reasonably aggressive without real risk.

  • Unit of counting: "rounds," not raw messages. A round = one HumanMessage plus everything the agent did in response (however many tool calls that took — AIMessage/ToolMessage pairs). Counting raw messages was considered and rejected: tool-call-heavy activity in a busy multi-user session would inflate the raw count fast and trigger summarization constantly, compounding lossy summaries on top of each other.
  • Window: 8 rounds kept verbatim. Once exceeded: summarize the oldest 4 rounds, keep the newest 4, folding the oldest into a running summary rather than discarding it.
  • Safety net: an independent raw-message ceiling (~40 messages) that can trigger summarization early regardless of round count, for the edge case where a single round is enormous (e.g. a giant pasted bill generating dozens of tool calls in one exchange).
  • Cut points must be round-aligned — this also guarantees a tool-call and its matching tool-response are never split across the summarized/kept boundary, which would otherwise produce a malformed conversation the LLM API would reject.
Changes — core/database.py
  • New migration: add chat_sessions.context_summary TEXT NOT NULL DEFAULT '', same idempotent pattern as the other migrations in this file.
  • New functions: get_context_summary(session_id) -> str, set_context_summary(session_id, summary: str) -> None.
Changes — agents/chat_agent.py
  • _agent_node: if context_summary is non-empty, inject it into the system prompt as an "EARLIER CONVERSATION (summarized)" section — parallel to how _pending_proposals_summary() is already appended.
  • New function (name it something like _maybe_summarize_and_trim): after a turn completes, count rounds in the current checkpoint's message list for this thread_id/session_id. If over threshold (per the numbers above), this is what gets scheduled as the background job — see server.py changes below for how it's invoked without blocking the response.
  • The actual summarization work (no lock held): take a snapshot of the oldest ~4 rounds' messages, call the session's already-configured chat model (no new provider config needed) to merge them into the existing context_summary, producing an updated summary string.
  • The trim/persist step (lock held briefly): re-fetch current checkpoint state under the per-session lock, confirm those specific message IDs still exist (defensive check against a race), remove them from the checkpoint, and call set_context_summary with the new summary. Verify the exact current LangGraph API for removing specific messages from a checkpointed state against whatever version is pinned in requirements.txt — LangGraph has a mechanism for this (a special message type that, when added via the graph's message reducer, deletes the referenced message by id) but don't assume exact syntax without checking the installed version's actual interface first.
Changes — server.py
  • In the chat and upload_image endpoints: after preparing the response (and releasing the per-session lock for the main turn), schedule the summarization check via FastAPI's BackgroundTasks (add it as a parameter to the endpoint, call background_tasks.add_task(...)) — this runs only after the HTTP response has already been sent, so the triggering user's reply has zero added latency.
  • The background task must acquire the per-session lock only for its final, fast persist step — never for the LLM summarization call itself — so a concurrent request from another user in the same session is never meaningfully blocked by a summarization run in progress.
Acceptance / manual test
  • Drive a session past 8 rounds, confirm summarization fires in the background (check context_summary gets populated, check the checkpoint's message count actually drops).
  • Confirm the triggering request's response time is unaffected (measure before/after).
  • Simulate a concurrent request arriving while summarization is mid-flight (e.g. a test that holds the LLM call artificially) and confirm it doesn't block waiting for the background job.
  • Confirm a single oversized round (many tool calls in one exchange) triggers the safety-net ceiling correctly even with round count still under 8.
  • Run the full test suite — no regressions expected elsewhere.
Non-goals

No UI surfacing of the summary — this is purely internal context management, invisible to users. No changes related to feedback #5 (agent chattiness) — that's a separate, deferred item.

TASK 11Ready now

Session title bug fix + WhatsApp-style title bar

Addresses feedback item #9. Depends on nothing.

Workflow: branch off multi-user (git checkout -b task11-session-title multi-user). Commit incrementally with meaningful messages. Open the PR against multi-user, not main.
Confirmed root cause

In server.py's chat/upload_image endpoints, the auto-rename trigger is if len(agent.state.bills) > prev_bill_count. This was correct before the proposal system existed; now add_bill only creates a pending proposal and doesn't touch state.bills until an admin approves it. In any session with an unapproved bill sitting pending, the rename condition never fires.

Backend fix
  • Change the trigger to also account for pending proposals: prev_count = len(agent.state.bills) + db.count_pending_proposals(session_id), computed before the turn; compare the same combined count after. If it increased, trigger the rename check.
  • _session_name_from_agent currently only looks at agent.state.bills[0]. If state.bills is empty but a proposal now exists, fall back to the first pending proposal's description (db.list_pending_proposals(session_id)[0]["payload"]["description"]).
  • New column: chat_sessions.title_auto INTEGER NOT NULL DEFAULT 1 (migration, same pattern as the rest of core/database.py). The auto-rename logic above must check this flag first and skip renaming entirely if the user has switched to manual naming (see frontend below).
Frontend: title bar

Add a small header bar above the chat panel (currently blank) showing the current session's name — matching the WhatsApp pattern of a persistent title bar above the message list, not just in the sidebar.

  • Click-to-rename inline edit in this new bar — can reuse the existing rename logic already wired up in the sidebar (startRename in frontend/app.js), just give it a second entry point here.
  • A toggle (e.g. a small switch or checkbox near the title) for "auto-generate title" vs. manual. Manually renaming should flip title_auto to 0 via a small addition to the existing rename endpoint/call; flipping the toggle back to "auto" sets it back to 1.
Acceptance / manual test
  • Start a fresh session, have two users converse and propose a bill without it being approved yet — confirm the title updates away from "New Session" immediately (not waiting for approval).
  • Manually rename a session, confirm title_auto flips to off and subsequent bill activity no longer overwrites the manual name.
  • Toggle back to auto, confirm renaming resumes.
TASK 12Ready now

Prompt fix: item categorization

Addresses feedback item #4. Depends on nothing.

Workflow: branch off multi-user (git checkout -b task12-prompt-categorization multi-user). Commit with a meaningful message. Open the PR against multi-user, not main.
Problem

The agent sometimes merges distinct items under one umbrella name — e.g. lumping whiskey into "beer" when the user said "we split beer." Reported across more than one tested scenario.

Decided scope — deliberately small

A targeted addition to the ## Rules section of SYSTEM_PROMPT_TEMPLATE in agents/chat_agent.py — not a rewrite. Outside of this one failure mode the current prompt is working well and must not be disturbed. Something like: "Treat each distinctly-named item/drink/product mentioned as its own line item. Never fold a different item (e.g. whiskey) into an existing item's name (e.g. beer) just because the user grouped them casually in conversation (e.g. 'we split the drinks'). If it's ambiguous which specific items are included in a casual grouping, ask for clarification rather than guessing." Adjust wording as needed, but keep the change confined to this one addition.

Acceptance

Manually re-test the original failure scenario (a dinner bill with both beer and whiskey, user says "we split beer") and confirm the agent keeps them as separate line items or asks for clarification, without regressing any other previously-working behavior. No automated test exists for prompt quality — this is necessarily a manual check.

TASK 14Ready now

Real-time sync via WebSocket

Addresses feedback item #1. Depends on nothing.

Workflow: branch off multi-user (git checkout -b task14-websocket-realtime multi-user). Commit incrementally with meaningful messages. Open the PR against multi-user, not main.
Context & research

See Testing Feedback #1 for the full research summary — WhatsApp/ Discord/Telegram all converge on a persistent-connection + in-process fan-out pattern at their scale; the sharding/Redis-routing machinery they need solves a "which of our many servers" problem this single-process app doesn't have. Only the core primitive applies here.

Changes — server.py
  • New WebSocket route: @app.websocket("/ws/sessions/{session_id}"). Authenticate during the handshake by reading the same access_token cookie the REST endpoints use (FastAPI WebSocket routes can read cookies off the handshake request) — reuse core.auth's existing JWT verification, no new auth mechanism. Reject the connection (close with an appropriate code) if the cookie is missing/invalid, or if the user isn't a member of session_id (reuse the same membership check _require_member uses).
  • New in-process registry: _session_sockets: dict[str, list[WebSocket]] — same shape and lifecycle as the existing sessions (ChatAgent cache) and _session_locks dicts already in this file. Add/remove the connection on connect/disconnect.
  • Broadcast trigger points: after _run_chat_turn completes (new chat message + updated state) and after approve_proposal/reject_proposal succeed, push an event to every open socket registered for that session_id — reuse whatever _serialize_state already produces for the state payload, and the same message shape GET /sessions/{id}/messages already returns for the new-message payload, so the frontend doesn't need to understand two different shapes for the same data.
  • Clean up _session_sockets entries in delete_session/end_session, same as the existing lock-cleanup pattern there.
Changes — frontend/app.js
  • When a session is loaded (loadSession), open a WebSocket connection to /ws/sessions/{id} alongside the existing REST fetches. Close the previous session's socket when switching sessions.
  • On an incoming message/state event, update the chat log and state panel in place — do not trigger a full page reload or re-run loadSession's full fetch sequence.
  • Keep all existing REST fetches exactly as they are — they still handle "catching up" when a session is first opened; the socket only needs to cover "stay live while already looking at it."
  • Handle reconnection reasonably (e.g. on socket close/error, attempt to reconnect, or at minimum fail gracefully back to "reload to see updates" rather than silently going stale with no indication).
Deliberately not doing (v1 scope)

No Redis, no offline message queue, no presence/typing indicators. These solve multi-server-instance problems this app doesn't have at its current scale, and aren't needed for the core "no manual reload" problem being fixed here.

Acceptance / manual test

Two real browser sessions (two accounts) open the same session. One sends a message — confirm the other sees it appear live, with no reload. One approves a proposal — confirm the other's state panel updates live. Confirm closing one tab doesn't affect the other's connection, and confirm a page reload cleanly re-establishes the socket.
